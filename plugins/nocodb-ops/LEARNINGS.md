# LEARNINGS.md

## 2026-10 — 100-record batches, sort objects, exactDate filters; no `nc` binary; MCP contract

**Problem:** Six defects, all present in 1.0.6 and checked against the live NocoDB MCP server (release 2026.09.1):
1. Docs said record writes take up to two thousand records per call (`createRecords`, `updateRecords`, `deleteRecords`) and recommended batches of a few hundred. The server's schema allows **100**, and a longer array is rejected outright — the whole call fails, nothing is truncated.
2. `sort` was documented as plain strings with a minus prefix for descending. The server wants an array of objects `[{field, direction}]` and answers a string with `Expected object, received string at sort[0]`. `pageSize` was documented as a default of twenty-five and a cap of two thousand; it is a default of 50 and a cap of 200 (the response reports the applied `page_size`).
3. Date filters put a bare calendar date right after the operator, and date ranges used `btw` (with or without `exactDate`). On Date / DateTime fields every comparison needs a `sub_operator` — a bare date is read as the sub-operator and rejected (`'<date>' is not supported`) — and `btw` / `nbtw` are rejected on Number, Decimal, Currency, Percent, Rating, Duration, Date / DateTime and Checkbox (`Operation btw is not supported for type Date`). Ranges are two bounds: `(d,gte,exactDate,A)~and(d,lte,exactDate,B)`.
4. The command-line recipes called a binary named `nc` (96 occurrences). NocoDB has none — on Linux/macOS `nc` is netcat. The official CLI is `scripts/nocodb.sh` of the `nocodb/agent-skills` skill, which reads `NOCODB_TOKEN`; the plugin documented a differently named variable.
5. The MCP contract was described as "11 tools" and setup pointed at an Integrations menu entry that no longer holds the MCP connection. Cloud and licensed servers list read tools and record writes directly (`whoami`, `groupByRecords`, `linkRecords`, `exportCsv`, …) and keep the rest behind `listTools(category)` → `callTool` (`upsertRecords`, `updateRecordsByCondition`, `linkRecordsByDisplayValue`, `importCsv`, `exportExcel`, trash tools). Community Edition still has the original eleven record tools. A 401 on the MCP token can also mean a revoked or restricted connection (its Tools & Permissions allowlist), not only an expired token.
6. `deleteRecords` was documented as always permanent. On a NocoDB-managed source deleted rows go to the base trash and can be restored (`listTrash`, `restoreRecords`, `restoreFromTrash`) inside the retention window; on an external source the delete is permanent.

**Fix:** Every batch figure is 100; every `sort` is an array of `{field, direction}` objects (only `groupByRecords.sort` keeps its single `-field` string); date examples carry `exactDate`; ranges are two bounds; the structured `filter` (`{field, operator, value[, sub_operator]}` or `{group_operator, filters[]}`) is documented as preferred over `where`, which stays as the fallback — pass only one of the two. `aggregate` examples now carry both required parameters (`aggregations`, `filterGroups`; one overall result is `filterGroups: [{alias: "All"}]`) — several examples used `aggregation` / a top-level `where`, `createRecords` examples omitted the `fields` wrapper, and `updateRecords` examples omitted `id` + `fields`. `thisMonth` (not a valid sub-operator) became explicit `exactDate` bounds, and "stale" examples that filtered `isWithin pastNumberOfDays` (the opposite) now use `lt daysAgo`. `cli-reference` became curl recipes on the v3 API mapped to `nocodb.sh` commands (the script is not vendored; `npx skills add nocodb/agent-skills`); `NOCODB_TOKEN` everywhere, with one legacy-alias line in `setup`. `mcp-patterns` carries the Community vs Cloud/licensed contract; `setup` starts with `whoami` and detects the edition with `listTools`. New content: `groupByRecords`, `upsertRecords`, `updateRecordsByCondition`, link tools, `exportCsv` / `exportExcel` / `importCsv`, trash restore. The README sends users of the deprecated `nocodb` plugin to `nocodb-dev` for schema work; the reference to a private plugin was removed. The setup/troubleshoot rows about the server being named `nocodb` (not `nocodb-1`) described the old bare-name failure; they now describe the real failure mode — the plugin's MCP server not starting because `NOCODB_MCP_URL` / `NOCODB_MCP_TOKEN` are unset — for the prefixed `mcp__plugin_nocodb-ops_nocodb__<tool>` names.
**Root cause:** The plugin was written from the 2025 MCP docs and never re-checked against the server's own tool schemas, which are the authority; the CLI recipes were copied from an upstream package whose binary name was never real on Unix.
**Severity:** Critical

## 2026-05-06 — Split env vars by transport (MCP vs REST)

**Problem:** A single `NOCODB_TOKEN` was reused for both the MCP `xc-mcp-token` header and the REST API token, even though those are distinct tokens minted in different NocoDB UI sections (the MCP connection vs Team & Settings → API Tokens). Sharing one variable forced users to pick which surface worked at any given time.
**Fix:** Split into two pairs — MCP uses `NOCODB_MCP_URL` + `NOCODB_MCP_TOKEN`, REST uses `NOCODB_URL` + an API-token variable. Updated `.mcp.json`, README, setup, troubleshoot, and cli-reference skills. Bumped to 1.0.6. **Corrected 2026-10:** the REST token variable was given the wrong name here; the official `nocodb.sh` script and the root `.env.example` use `NOCODB_TOKEN`, so that is the name now (see the 2026-10 entry). The MCP/REST split itself stands.
**Root cause:** Initial scaffolding conflated the two transports because both happen to authenticate with a NocoDB-issued token string.
**Severity:** Major

## 2026-04-07 — MCP server naming and URL auth error

**Problem:** MCP server was named `nocodb-1` instead of `nocodb`, causing tool name mismatches. Additionally, users setting `NOCODB_URL` without the `/mcp` path got "Protected resource does not match" auth errors.
**Fix:** Renamed MCP server from `nocodb-1` to `nocodb` across all 19 files. Updated docs to clarify that `NOCODB_URL` must be the full MCP endpoint URL including `/mcp/{path-id}` (e.g., `https://host/mcp/ncc17zpg5n7v9vs8`). Auth uses `xc-mcp-token` header — NOT OAuth2.
**Root cause:** The `-1` suffix didn't match convention. Docs showed incomplete URL examples without the path ID suffix, leading users to use just the base URL.
**Severity:** Critical

## 2026-10-03 — webhooks: new skill, moved in from `stack-composable-stack-v1`

**Problem:** The only NocoDB webhook reference in the workspace for the receiving side sat in the stack plugin (`nocodb-to-n8n`), and it was wrong: it listed events `records.after.bulkInsert` / `bulkUpdate` that the docs do not have (After Insert / Update / Delete already cover one or more records), showed a payload without `id`, `version`, `view_id` and `view_name`, and said nothing about conditions, the Button trigger or the paid-plan sources (View, Field, Comment). `nocodb-dev:webhooks` covers creating hooks (HookV3, notification types) but not what the receiver gets.
**Fix:** New `skills/webhooks/SKILL.md` from the NocoDB "Create Webhook" docs and the live MCP `hooks` category: events by source and edition, UI steps, the v3 payload (`data.rows` array, `previous_rows` on update), the not-met-to-met condition rule, the Button trigger, `listHooks`/`getHook` (listed) versus `createHook`/`updateHook`/`deleteHook` (behind `listTools hooks`; full replacement on update). It links to `nocodb-dev:webhooks` instead of repeating hook configuration. The syntax of `queryRecords`/`createRecords` that the stack carried is already in `mcp-patterns` (`pageSize`, `filter`, `records[{fields}]`) and was not copied.
**Root cause:** Business-side webhook knowledge had no home in the technology plugins, so the stack plugin invented its own. Open for the owner: `nocodb-dev:webhooks` says the destination payload carries `record` / `records`, the docs sample shows `data.rows`; one live test of a record webhook would settle which shape a custom body templates against.
**Severity:** Major
