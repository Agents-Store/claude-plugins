# Learnings

## 2026-10-03 — whole plugin: renamed from `stack-directus-nextjs-dev`, architecture only (2.0.0)

**Problem:** The plugin taught SDK calls, Docker, NextAuth and Next.js caching in depth next to the boundary rules, and several of those rules were wrong. `rest({ cache: 'no-store' })` does not compile (`RestConfig` is `credentials`, `onRequest`, `onResponse`: TS2353) and the "Next.js force-caches fetch" premise behind it is false since Next.js 15; `revalidateTag(tag)` ran with one argument and no read ever carried a tag, so nothing could be invalidated; `directusAsset()` appended the administrator token as `?access_token=` and the skill claimed `next/image` keeps it hidden, but `next/image` writes the whole source URL into the HTML, so every visitor received the admin token (the 2026-03-30 entry below added that parameter; this supersedes it); `readItems('directus_collections')` is a type error and throws at runtime; `middleware.ts` is `proxy.ts` in Next.js 16; the health check called `/server/health`, which needs a token in Directus 12; the revalidation secret travelled in the URL; dotted `fields` strings (`'author.name'`) do not type-check in SDK 26; a price typed `number` arrives as a string; a Server Action used the admin token without checking who called it; NextAuth v4 was the only auth path described.
**Fix:** Variant A (decision 2026-09-06): a stack describes the architecture and names its parts in `dependencies` (`directus-dev`, `nextjs-dev`); a skill stays when it links two or more tools and moves out when it explains one. Moved: the SDK client, `readItems`, relations, types, singleton and filter patterns to `directus-dev:sdk-patterns` (`references/ssr-client.md`, `references/content-queries.md`); the login and refresh contract and CORS to `references/ssr-client.md`; the Directus Compose file to `directus-dev:docker-local-dev` (already there, updated); the Flow-to-route webhook to `directus-dev:flow-automation` (`references/notify-external-app.md`) and `nextjs-dev:data-fetching` (`references/headless-cms.md`, together with `generateStaticParams`, Server Actions and the `next.config.ts` images block); the NextAuth config, provider, `proxy.ts` and login page to `nextjs-dev:auth-patterns` (`references/nextauth-and-authjs.md`). Kept and rewritten thin: `directus-to-nextjs` (token, cache, assets, types), `authentication` (one page: who owns the session and the tokens, three paths, NextAuth v4 working path, Better Auth for new projects), `deployment` (pipeline and production checklist), `init-project`, `full-feature`, `examples`, the agent and the templates. New rules: every read is tagged with the collections it reads and a Flow expires the tag through `/api/revalidate` (secret in a header, tag allow-list); assets are either public (Core tier: unrestricted read on `directus_files`, so every file becomes listable) or served by a proxy route restricted to one folder; no token in any URL a browser sees; `requireUser()` before the server token is used. The MCP tool prefix is now `mcp__plugin_stack-directus-nextjs_directus__`.
**Root cause:** The plugin was written when no technology plugin existed and was never re-checked against `@directus/sdk` types, Next.js 15/16 caching behaviour or Directus 12. The asset fix of March assumed `next/image` hides the URL.
**Severity:** Critical (token leak, non-compiling recipe). Breaking: the plugin is renamed `stack-directus-nextjs-dev` to `stack-directus-nextjs` (the marketplace `renames` map moves installed copies; update `enabledPlugins` entries and skill references such as `stack-directus-nextjs-dev:directus-to-nextjs`), hence 2.0.0.

**Update 2026-10-03 (review):** (a) Server Actions and the `full-feature` template authenticated but did not authorize: `requireUser()` followed by a write with the server token let any signed-in user change any item by id. The template now writes with `withToken(session.accessToken, ...)` so Directus applies the user's policies (Better Auth path: a role or ownership check in code), and the rules in `authentication`, `directus-to-nextjs`, the agent and the project template say "authenticate and authorize". (b) The recipes of `directus-dev` and `nextjs-dev` read `DIRECTUS_URL` and `DIRECTUS_TOKEN`, the stack defines `NEXT_PUBLIC_DIRECTUS_URL` and `DIRECTUS_ADMIN_TOKEN`: the NextAuth login called `undefined/auth/login`. `templates/.env.example` now defines the two recipe names as `${...}` references to the stack's (Next.js expands them in `.env` files), and `authentication`, `init-project`, `deployment` and the README say so. (c) The asset proxy serves only raster `image/*` (no SVG, no HTML), with `X-Content-Type-Options: nosniff`; the Core-tier permission refusal is labelled as seen on Directus 12.4.1.

## 2026-03-30 — directus-to-nextjs: Missing access_token in directusAsset helper

**Problem:** The `directusAsset()` helper function constructed image URLs without authentication. When the Directus public role doesn't have read access to `directus_files`, all images served via `next/image` break silently with 403 Forbidden — the most common integration gotcha.
**Fix:** Added `access_token` parameter to the helper function. Added a table documenting three authentication approaches (token in URL, public role, API route proxy) with guidance on when to use each.
**Root cause:** The skill assumed Directus files are publicly accessible by default. In practice, most Directus instances require authentication for file access.
**Severity:** Major
