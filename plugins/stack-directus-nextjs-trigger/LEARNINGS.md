## 2026-10-03 — whole plugin: renamed from `stack-directus-nextjs-trigger-dev`, architecture only (3.0.0)

**Context**: freshness pass against Trigger.dev 4.7.2, Directus 12.4.1, `@directus/sdk` 26 and Next.js 16.3.8; variant A of the stack split (decision 2026-09-06).
**What happened**: besides the Directus and Next.js errors of the sibling stack (`rest({ cache })` does not compile, no read ever carried a cache tag, an administrator token travelled in image URLs, `readItems('directus_collections')`, `middleware.ts`, `/server/health`, secrets in URLs), this plugin taught the deprecated `@trigger.dev/sdk/v3` import path (v3 is end of life; the path still resolves in 4.7.2) and Trigger.dev API that does not exist in 4.7.2: `deploy --self-hosted` and `schedules:attach` (`error: unknown option` and `unknown command` on the 4.7.2 CLI); `TriggerProvider` (not exported by `@trigger.dev/react-hooks`; the context is `TriggerAuthContext`); `tasks.triggerAndPoll` (not a property of `tasks`; `triggerAndWait` and `triggerAndSubscribe` work only inside a task, `runs.poll` from backend code); `retry.attempt` in `catchError` (a TypeScript error); the MCP tool `run_task` (it is `trigger_task`); "schedules are not active until attached" and "dev does not fire schedules" (both wrong); `export const dynamic = 'force-dynamic'` as mandatory (the SDK reads its environment on the first call, not on import). Design errors too: a user's access and refresh token in the task payload (a payload is stored with the run and readable in the dashboard; the access token lives 15 minutes and the refresh token is single use); the HMAC computed in a Directus Run Script (isolated context, no `crypto`); the loop guard written as an expression (`{{ $trigger.payload.body }} != null`) where the condition operation takes filter rules; a secret set under a Directus settings page that does not exist; a secret in the Flow URL and compared with `!==`; the Flow and the revalidation route sharing one secret; an idempotency key built from the item id (it blocks every later edit while the key is remembered); a realtime hook with no `baseURL` (the default is Trigger.dev Cloud) and a claim that the run token "expires when the run finishes" (it lasts 15 minutes by default); `r.rate.toFixed(4)` on a decimal field, which Directus returns as a string.
**Root cause**: the plugin was written before technology plugins existed and was never re-checked against the SDK types, the CLI help or the Directus code. The `.env.local` aliases that bridge the stack's variable names to the recipes' names work for Next.js, which expands `${VAR}`, but the Trigger.dev CLI loads `.env.local` for `trigger dev` without expanding, so a task read the literal text `${NEXT_PUBLIC_DIRECTUS_URL}` (checked with the CLI's own dotenv loader, 4.7.2).
**Fix**: variant A: the stack describes the architecture and names its parts in `dependencies` (`directus-dev`, `nextjs-dev`, `trigger-dev`); a skill stays when it links two or more tools and moves out when it explains one. Moved: `scheduled-tasks` (cron, timezones, windows, imperative schedules, testing, idempotent runs, "when a schedule does not fire") to `trigger-dev:scheduled-tasks`; the Next.js token handoff, `baseURL`, token lifetime, `refreshAccessToken` and `TriggerAuthContext` to `trigger-dev:realtime`; starting runs from a route or action, `batchTrigger`, `runs.poll` and the build-time error to `trigger-dev:task-development` (`references/triggering-patterns.md`); the Flow settings (item keys, the write-back loop guard, signing limits) to `directus-dev:flow-automation` (`references/send-items-to-a-worker.md`); the Directus SDK, Compose, NextAuth and Next.js caching copies are the same ones as in `stack-directus-nextjs` and point at `directus-dev` and `nextjs-dev`. Deleted from this plugin: the `scheduled-tasks` skill, the Compose file, the NextAuth configuration. Kept and rewritten thin: `background-tasks` (what crosses the boundary, authorize before the trigger, the run token, closing the loop), `directus-to-trigger` (the Flow's values, the receiver, the task-side client, loop guards), `authentication` (one page; "Authenticated Tasks"), `deployment` (four pipelines, variables per service, task deploys, checklist), `init-project`, `full-feature` (a background-work step), `examples` (four scenarios), the agent and the templates. New rules: a task has its own Directus user and environment; a payload is ids and `requestedBy`; editor saves are debounced and the task skips unchanged work by a source hash; the receiver checks a header secret with `timingSafeEqual` and an allow-list of collections; `trigger dev` runs with `--env-file .env.trigger.local` (literal values); the Trigger.dev CLI, SDK, hooks and server are one version; `TRIGGER_API_URL` must be set where a run is triggered. The MCP prefix is now `mcp__plugin_stack-directus-nextjs-trigger_<server>__` and the Trigger.dev server starts with `--dev-only --project-ref`; `.mcp.json` can pin the CLI through `TRIGGER_CLI_VERSION`.
**Lesson**: a stack is a set of boundaries, and each boundary needs its own credential and its own environment; anything that explains one tool belongs in that tool's plugin, where it is checked against that tool's types.
**Severity**: Critical (a user token stored in payloads, non-compiling recipes, commands that do not exist). Breaking: the plugin is renamed `stack-directus-nextjs-trigger-dev` to `stack-directus-nextjs-trigger` (the marketplace `renames` map moves installed copies; update `enabledPlugins` entries and skill references), hence 3.0.0.

## 2026-09-30 — Trigger.dev MCP authenticates with TRIGGER_ACCESS_TOKEN, not TRIGGER_SECRET_KEY

**Context**: checking every credential of the test workspace against the Trigger.dev docs
**What happened**: `.mcp.json` fed `TRIGGER_SECRET_KEY` to the MCP server as `TRIGGER_ACCESS_TOKEN`. An environment key (`tr_dev_…`) gets 401 from the account-level tools (`whoami`, `list_projects`), so the README told people to put a PAT into `TRIGGER_SECRET_KEY` — which then no longer matched the name the SDK and the docs give that variable.
**Root cause**: one variable was made to carry two different credentials.
**Fix**: the MCP server reads `TRIGGER_ACCESS_TOKEN` (a PAT); `TRIGGER_SECRET_KEY` is only the environment key again. README, `.env.example` and `init-project` list both. Major bump — an existing project must add `TRIGGER_ACCESS_TOKEN` or the MCP server starts unauthenticated.
**Lesson**: a PAT and an environment key are different credentials; give each its documented name.
